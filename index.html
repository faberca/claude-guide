Claude Code 설치 가이드

Claude Code는 내 컴퓨터에 설치해서 쓰는 AI입니다. 웹 채팅처럼 파일을 올리고 답을 복사해 붙일 필요 없이, 폴더 안의 파일을 직접 읽고 고칩니다.

  • 복사·붙여넣기가 없어집니다. 파일 20개를 고쳐도 요청 한 번이면 됩니다.
  • 바로 쓸 수 있는 결과를 받습니다. 만든 것을 직접 실행해 보고, 오류가 나면 스스로 고칩니다.
  • 같은 설명을 반복하지 않습니다. 규칙을 CLAUDE.md에 한 번 적으면 그 폴더에서는 매번 따릅니다.

OpenAI의 Codex CLI도 같은 방식입니다. 규칙 파일 이름이 AGENTS.md인 것처럼 세부만 다릅니다. 이 가이드는 Claude Code 기준입니다.

내 지침과 스킬 만들기

앱에서는 짧은 지침부터, 반복 작업은 스킬로 나누세요.

01

어디서 사용하나요?

앱마다 지침을 넣는 곳이 달라요. 지금 쓰는 화면을 골라주세요.

02

내가 원하는 답변 정하기

공통 취향만 짧게 적고, 업무별 자료와 절차는 나중에 나눠두세요.

입력한 내용은 저장하거나 서버로 보내지 않습니다. 이름·계정·고객정보는 넣지 마세요.

03

새 대화에서 한 번 시험하기

위 안내의 위치에 저장한 뒤 새 대화를 여세요. AI가 “기억했어요”라고 답한 것만으로 적용을 판단하지 마세요.

원하는 길이·말투·근거가 나오는지 보고, 안 맞는 지침 한두 줄만 고쳐보세요. 수정·삭제도 저장한 설정이나 파일에서 합니다. 프로젝트마다 다른 목적과 자료는 해당 프로젝트 지침에 두세요.

메뉴가 없거나, 어디에 넣을지 모르겠어요

앱 업데이트와 조직 설정을 확인하고 아래 공식 안내를 열어보세요. 우선 현재 대화에 지침을 붙여 넣어 시험할 수도 있습니다. 이 경우 새 대화에도 자동 적용되는 것은 아닙니다.

파일을 다루는 에이전트에게는 “기존 지침을 먼저 읽고 필요한 내용만 합쳐줘. 공통 지침은 짧게 두고 상세 절차는 해당 작업에서만 읽도록 나눠줘. 실제 저장 위치와 확인한 결과를 알려줘”라고 요청하세요.

04

자주 반복하는 일만 스킬로 만들기

지침은 평소의 약속, 스킬은 특정 작업에서 꺼내 쓰는 절차입니다. 메모리는 이전 맥락을 참고하는 보조 기능입니다.

바로 써볼 예시: 원문을 지키는 문장 교정

원문의 뜻·말투·수치를 보존하고, 수정본을 다시 읽어 어려운 표현과 반복을 줄이는 스킬입니다. 파일을 자동 수정하거나 외부로 보내지 않습니다.

교정 스킬 ZIP 받기내용 먼저 보기

ZIP에는 proofread/SKILL.md 한 파일만 들어 있습니다. 사용 예: “이 글을 원문 말투를 유지하며 교정해줘.”

지침이 길어지거나 외부 스킬을 추가하고 싶어요

최상위에는 자주 쓰는 선호만 남기고, 반복 절차는 해당 스킬로 옮기세요. 설치한 스킬의 이름·설명으로 고른 뒤 필요한 본문과 참고자료만 읽도록 구성합니다. 파일을 나누고 모두 매번 읽게 하면 길이는 줄지 않습니다.

조사에는 근거 확인, 글쓰기에는 원문 보존과 두 번 교정, 구현에는 실제 동작 검사를 가져오면 좋습니다. 디자인용 Hallmark·UI/UX Pro Max나 영상 도구는 그 작업을 할 때 검토하세요. Threads에서 모은 디자인 개선 자료는 디자인스킬에 있습니다.

외부 스킬은 공식 출처·라이선스·필요 권한·실행 코드를 확인하세요. 스킬 설명 파일만 복사해도 필요한 도구까지 설치되는 것은 아닙니다. 비밀번호·토큰·개인 업무 자료를 공유 스킬에 넣지 마세요.

Claude Code에서 더 해보기

아래 명령과 파일 경로는 Claude Code용입니다. 일반 채팅 앱은 위 설정 안내를 이용하세요.

CLAUDE.md 만들기

Claude Code는 작업 프로젝트의 CLAUDE.md를 지침으로 읽습니다. 기존 파일을 먼저 확인하고 공통 규칙만 짧게 적으세요. 일반 채팅 앱은 위 설정란을 사용하세요.

/init

프로젝트를 분석해서 CLAUDE.md 초안을 자동 생성

검증 기준 주기 (가장 중요)

Claude는 "다 된 것 같으면" 멈춥니다. 통과·실패가 나오는 검사(테스트, 빌드, 비교 스크립트)를 주면 고치고 다시 돌리기를 스스로 반복합니다. 검사가 없으면 사람이 테스트 역할을 하게 됩니다.

validateEmail 함수 만들어줘. test@example.com은 true, invalid는 false로. 테스트도 만들고 실행해봐.
코드베이스 질문하기

새 프로젝트에 투입됐을 때, 선배한테 물어보듯이 질문하세요.

이 프로젝트의 폴더 구조와 각 역할을 설명해줘
로그인 기능이 어떻게 구현되어 있는지 알려줘
작업 도중 방향 잡기

설정보다 효과가 큰 습관입니다. 시작하고 첫 1분은 지켜보세요.

엉뚱한 쪽으로 가면
Esc
멈추고 바로 다시 지시. 한 일은 남음
시도를 되돌리려면
/rewind
빈 입력창에서 Esc 두 번도 같음
두 번 고쳐도 틀리면
/clear
세 번째 수정 대신, 배운 점을 담은 새 지시
Plan Mode: 탐색 → 계획 → 실행

큰 작업은 바로 코딩하지 말고, Plan Mode에서 먼저 파악하세요. /plan으로도 들어갑니다.

// 계획 승인 후 실행 모드로
계획대로 구현해줘. 테스트도 작성하고 돌려봐.
컨텍스트 관리

지금 모델은 100만 토큰을 담고, 넘치기 전에 자동으로 압축해서 공간이 모자랄 일은 드뭅니다. 그래도 주제가 바뀌면 /clear가 좋습니다. 답이 선명해지고 비용이 줄어요.

주제 전환
/clear
대화 압축
/compact API 변경에 집중
이전 대화
claude --continue
되돌리기
/rewind (Esc 두 번)

되돌리기는 Claude가 직접 고친 파일만 복원합니다. 명령(Bash)으로만 바뀐 파일은 Git으로 되돌리세요.

인터뷰 시키기

큰 기능을 만들 때, Claude에게 먼저 질문하게 하세요. 놓치기 쉬운 엣지케이스를 잡아줍니다.

[기능 설명] 만들고 싶어. 먼저 나한테 질문해봐.
기술 구현, UX, 엣지케이스, 트레이드오프를 파고들어.
다 끝나면 SPEC.md로 정리해줘.

SPEC.md가 생기면 /clear 후 새 대화에서 "SPEC.md대로 만들어줘"로 시작하세요. 깨끗한 상태에서 완료 기준이 적힌 채로 시작합니다.

커스텀 스킬 만들기

반복 워크플로우를 /스킬이름으로 즉시 실행. .claude/skills/에 SKILL.md 파일 추가.

# .claude/skills/fix-issue/SKILL.md
---
name: fix-issue
description: GitHub 이슈 자동 수정
---
1. gh issue view $ARGUMENTS로 이슈 확인
2. 관련 파일 찾기
3. 수정 구현 + 테스트
4. PR 생성

사용: /fix-issue 1234

행동 규칙 (.claude/rules/)

Claude Code의 rules/에는 주제별 규칙을 둘 수 있습니다. 규칙을 추가한 뒤 작은 작업으로 실제 반영을 확인하세요.

# .claude/rules/verification.md
작업 완료 시 반드시 보고:
- 변경 파일 목록
- 실행한 검증 명령 + 출력
- 수치 증거
- "잘 됩니다" 같은 증거 없는 보고 금지
서브에이전트 & 병렬 세션

서로 독립된 일을 동시에 돌리거나, 긴 출력을 따로 떼거나, 내 생각을 모르는 눈으로 검토받을 때 씁니다. 같은 일을 넘긴다고 답이 좋아지지는 않고 토큰은 더 듭니다.

서브에이전트를 써서 인증 시스템의 토큰 갱신 로직 조사해줘

Writer/Reviewer 패턴: 세션 A에서 구현 → 세션 B에서 리뷰 → A에서 피드백 반영

스크립트에서 한 번 실행

-p는 대화 없이 한 번 실행하고 끝냅니다. 허용할 도구를 좁혀서 쓰세요.

claude -p "README.md 요약해줘" --allowedTools "Read"

자동 실행은 내용을 아는 폴더에서만 쓰세요. -p는 그 폴더의 hook·MCP 설정을 신뢰 확인 없이 실행합니다.

Hooks · MCP · Plugin

Hooks = Claude 행동에 자동 반응하는 스크립트. MCP = 외부 도구(Notion, DB, Figma) 연결. Plugin = 스킬·hook·MCP 묶음으로 /plugin에서 설치합니다. 플러그인은 내 권한으로 코드를 실행하니 출처를 확인하고 필요한 것만 켜세요.

파일 수정할 때마다 eslint 자동 실행하는 hook 만들어줘

짧게 시작하는 프로젝트 스타터킷

공통 지침은 짧게, 자세한 절차는 필요할 때 읽도록 구성했습니다. 앱 채팅만 쓰는 분은 위의 지침 만들기로 시작하세요.

CLAUDE.md

한국어·근거·원본 보존·검증 등 짧은 공통 규칙. 긴 결과는 MD로 받는 선호는 직접 선택합니다.

필요할 때 읽는 참고자료

.claude/references/guide-workflows.md에 조사·문서·큰 변경 절차를 둡니다. 항상 읽는 rules 파일은 새로 설치하지 않습니다.

개발용 스킬 3개

/commit-flow, /review, /explain. 해당 작업을 요청할 때 사용하고, 기존 같은 이름의 파일은 보존합니다.

Windows용 설치 스크립트 보기·받기

프로젝트 폴더에서 사용하세요. 먼저 스크립트 내용을 읽고 실행하세요. 기존 파일은 건너뛰며, 새로 만드는 파일은 설치 결과에 표시합니다.

setup.ps1 내용 보기
Invoke-WebRequest https://claude-guide-sandy.vercel.app/starter-kit/setup.ps1 -OutFile setup-guide.ps1
notepad .\setup-guide.ps1
# 내용을 확인한 뒤 실행
.\setup-guide.ps1

스크립트 실행 정책이 막으면 보안 설정을 일괄 해제하지 말고, 위 파일과 CLAUDE.md 내용을 확인해 필요한 파일만 직접 추가하세요.

기존 스타터킷을 설치했다면

다시 실행해도 기존 CLAUDE.md와 .claude/rules는 바뀌지 않습니다. AI에게 기존 규칙을 먼저 비교하게 하고, 반복 규칙과 상세 절차를 필요한 문서로 옮기세요. 기존 파일을 자동 삭제하지 않습니다.

새 세션에서 작은 작업을 시킨 뒤 지침을 읽었는지와 결과가 원하는 방식인지 함께 확인하세요. 파일 생성과 실제 적용은 별개입니다.

1

          

            
컨텍스트 = 지금 대화에서 Claude가 보고 있는 것

            
Claude는 대화·읽은 파일·명령 결과를 "컨텍스트"에 담고 답합니다. 지금 모델은 100만 토큰까지 담고, 넘치기 전에 자동으로 요약·압축하기 때문에 공간이 모자랄 일은 드뭅니다. 문제는 양보다 섞임입니다. 관계없는 이야기가 쌓이면 답이 흐려지고 비용도 늘어납니다.


            
            

              claude> 안녕!
              
Opus 5.5 · 120k/1M · ↑ 응답 중...

            

            
예시 화면입니다. 상태줄에 무엇을 띄울지는 /statusline으로 정할 수 있습니다. 숫자 기준을 외울 필요는 없고, 주제가 바뀌면 /clear를 습관으로 두세요.


            

              

                
/clear

                
주제 바뀌면 새로 시작. 답이 선명해지고 비용이 줄어듦. 가장 중요한 습관.

              

              

                
/compact

                
같은 주제를 이어가며 핵심만 남기기. 자동으로도 되지만 "API 변경에 집중"처럼 남길 것을 지정할 수 있음.

              

              

                
한 대화 = 한 주제

                
사이트 만들기 + 소설 교정을 한 대화에서 하면 둘 다 결과가 나빠짐.

              

            

          

        

      


      
      

        

          
2

          

            
CLAUDE.md = 매번 자동으로 읽는 설명서

            
프로젝트 폴더에 CLAUDE.md 파일을 넣어두면 매 대화 시작할 때 Claude가 자동으로 읽습니다. "나는 이렇게 해줘"를 매번 말할 필요 없음.

            

              

                
넣으면 좋은 것

                
"한국어로 답변해", "결과는 파일로 저장해", "추측하지 말고 확인해", "내 문체는 ~야"

              

              

                
안 넣어도 되는 것

                
폴더 구조·코드 규칙처럼 Claude가 파일을 읽으면 알 수 있는 것. 넣기 전에 "읽으면 알 수 있나? 실제로 찾아볼까?" 둘 다 예면 빼세요. 매 대화마다 읽으니 짧을수록 좋습니다.

              

            

          

        

      


      
      

        

          
3

          

            
환각 방지 = "확인하고 말해"

            
AI는 모르는 것도 그럴듯하게 지어냅니다. Claude Code는 파일을 직접 읽을 수 있어서 훨씬 낫지만, 규칙을 안 잡으면 여전히 추측합니다.

            

              

                
CLAUDE.md에 한 줄

                
"중요한 주장은 파일이나 출처를 확인하고 답해줘." — 답변의 근거를 직접 대조하세요.

              

              

                
"진짜야?" 습관

                
의심되면 "그거 어디서 확인한 거야?" 물어보기. Claude가 근거를 못 대면 지어낸 것.

              

              

                
검증 강제

                
"증거 없이 '됐다'고 하지 마" 규칙 넣으면 결과물+근거를 같이 보여줌.

              

            

          

        

      


      
      

        

          
4

          

            
파일 = 영구 기억

            
대화는 사라지지만 파일은 남습니다. 중요한 건 항상 파일로 저장시키세요. 다음 세션에서 그 파일을 읽으면 기억이 이어집니다.

            

              

                
나쁜 예

                
"경쟁 제품 가격 알려줘" → 채팅으로 읽고 끝 → 다음에 또 물어야 함

              

              

                
좋은 예

                
"경쟁 제품 가격 조사해서 출처와 함께 research/가격비교.md로 저장해" → 영구 보존 → 다음에 바로 참조

              

            

          

        

      


      
      

        

          
5

          

            
인터넷에 도는 옛 요령, 이제는 안 해도 됩니다

            
SNS 팁 중에는 예전 모델용 우회법이 많습니다. Anthropic 공식 모범 사례(2026년 11월 기준)는 아래 습관을 버려도 된다고 정리합니다.

            

              
옛 요령지금은

              
                
지시에 IMPORTANT, 대문자로 강조평범하게 한 줄로 쓰면 따릅니다. 강조를 쌓으면 오히려 과하게 적용합니다. 꼭 지켜야 하면 hook이나 금지 규칙으로.

                
"think hard", "꼼꼼히 생각해"평범한 문장일 뿐 생각 강도를 올리지 않습니다. 그 턴만 깊게 생각시키려면 ultrathink를 쓰세요.

                
"게으르지 마, 끝날 때까지 계속해"합의한 일은 알아서 이어갑니다. 이런 문장은 과한 작업을 부릅니다. 대신 통과해야 할 검사를 주세요. 멈추면 "계속"이라고만 하면 됩니다.

                
CLAUDE.md에 폴더 구조 설명Claude가 직접 읽습니다. 파일에 없는 것(결정 이유, 배포 절차, 금지 사항)만 적으세요.

                
컨텍스트를 아끼려고 수시로 압축공간 부족은 드뭅니다. 다만 주제가 바뀔 때 /clear는 여전히 좋습니다.

              
            

            
반대로 아직도 효과 있는 한마디: 원하는 범위가 클 때 "be ambitious(빈 상태·오류 처리까지 다 해줘)"처럼 기대 범위를 말해 주면, 최소한만 만들고 멈추는 일이 줄어듭니다. 출처: Claude Code Best practices
